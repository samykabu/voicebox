Arabic TTS & Voicebox

A consolidated summary of the Docker deployment, Arabic voice-cloning integration, GPU and quality fixes, Windows packaging, history management, and the architectural decisions made along the way.

Implementation complete Docker-first NVIDIA CUDA Arabic voice cloning

Executive outcome

We delivered a Docker-only Arabic text-to-speech and zero-shot voice-cloning stack, then integrated the same Arabic F5/Habibi model family natively into the Voicebox application. The solution keeps Python, PyTorch, CUDA user-space libraries, FFmpeg, TTS packages, and model weights off the Windows host while giving Voicebox a unified workflow for profiles, generation, history, model management, and GPU execution.

2 Standalone Arabic WebUIs retained on ports 7860 and 7861
8 Arabic F5/Habibi model variants in one Voicebox engine family
2 NVIDIA GPUs visible inside the validated CUDA container
0 ML runtime packages required on the Windows host
Final architecture: keep the proven standalone portals for direct model work, and provide a native f5_tts engine inside the Dockerized Voicebox runtime. This replaced the earlier remote-adapter recommendation after the Romanian F5 implementation in upstream PR #833 demonstrated a practical native path.

What we did

  1. Researched the Arabic TTS landscape. Evaluated F5-TTS, Habibi-TTS, existing Arabic-capable Voicebox engines, dependency constraints, licensing, voice-cloning requirements, and integration alternatives.
  2. Built the standalone Docker deployment. Created two GPU-enabled services: F5 Arabic MSA on port 7860 and Habibi Arabic on port 7861, with persistent model and Gradio caches and no host-side ML installation.
  3. Diagnosed and hardened both portals. Fixed container startup issues, Arabic model selection, reference-audio clipping, lazy checkpoint loading, microphone waveform visibility, and recorded-audio playback behavior.
  4. Compared Voicebox integration options. Documented direct Gradio calls, a stable REST adapter, native embedding, and a generic provider architecture. The initial recommendation favored a versioned REST adapter because it minimized dependency risk.
  5. Reviewed upstream F5 work and revised the plan. Upstream PR #833 showed how F5-TTS could fit Voicebox's existing backend protocol. We adopted that native pattern, removed Romanian assumptions, and hardened it for an Arabic multi-checkpoint catalog while retaining Docker as the release gate.
  6. Implemented native Arabic F5/Habibi support. Added backend lifecycle management, exact Arabic prompt handling, model switching, dialect conditioning, frontend model selection, model metadata, Docker packaging, tests, and operator documentation.
  7. Improved TADA and multi-GPU behavior. Added available-memory CUDA device selection and language-specific prompt aligners so Arabic generation is not forced through an English alignment path.
  8. Added Windows MSI automation. Built a GitHub Actions workflow for an installable Tauri MSI, then constrained it to run only after a pull request is merged.
  9. Added safe bulk history deletion. Implemented per-row selection, server-wide select-all, exclusions, confirmation, active-job protection, file cleanup, strict API validation, and SQLite-safe batching.
  10. Closed the review loop. Audited automated and human review comments, implemented valid feedback, replied with evidence, resolved every conversation, and reran CI and container checks.

Decision record

Area Decision Reason Status
Host isolation Run the ML stack in Docker. Meets the no-host-install requirement and makes the CUDA/PyTorch ABI reproducible. Adopted
Voicebox integration Use a native backend in Docker, while preserving standalone portals. PR #833 supplied a workable native pattern; Docker contains the dependency risk. Revised & adopted
Engine model Expose one f5_tts engine with model variants. Habibi builds on F5; one family avoids duplicated backend and UI logic. Adopted
Default model Use habibi-msa as the default. It is the specialized Arabic MSA checkpoint already proven in the standalone F5 portal. Adopted
Arabic text Preserve exact Arabic, including diacritics. Silent transliteration or letter normalization can change pronunciation and meaning. Adopted
TADA alignment Select prompt aligners by language. Arabic should not use an English-only alignment path. Adopted
GPU placement Expose all GPUs; choose a device using available memory. Visibility enables scheduling, while one inference process normally uses one GPU rather than pooling VRAM. Adopted
Dependency control Pin PyTorch 2.8, CUDA 12.8, Torchaudio 2.8, TorchCodec 0.7, F5-TTS 1.1.21, and Habibi-TTS 0.1.1. F5/Habibi and audio codecs are sensitive to binary compatibility changes. Adopted
MSI CI Build the Windows MSI only after a PR merge. Avoids expensive duplicate installers during review while still producing a post-merge artifact. Adopted
Bulk deletion Make select-all server-wide and protect active jobs. Infinite-scroll rows must not define deletion scope, and running synthesis must never be removed. Adopted
SQLite safety Query selected IDs in batches of 500 and filter large exclusions in Python. Prevents bound-variable limit failures on large histories. Adopted

Implemented solution

Standalone Arabic deployment

  • F5 Arabic MSA WebUI on 127.0.0.1:7860.
  • Habibi Arabic WebUI on 127.0.0.1:7861.
  • Dedicated GPU defaults with all GPUs visible to both containers.
  • Persistent Hugging Face/Torch and Gradio temporary-file volumes.
  • Lazy Habibi checkpoint loading to prevent avoidable VRAM exhaustion.
  • Recorder waveform/playback fix using container-native temporary storage.
  • Reference clipping fix so audio and transcript stay aligned.

Native Voicebox engine

  • One f5_tts backend and eight canonical Arabic model IDs.
  • MSA, Unified, Saudi, UAE, Algerian, Iraqi, Egyptian, and Moroccan variants.
  • Reference audio plus exact transcript required for cloning.
  • Arabic-aware long-text chunking and cross-fading.
  • Unified dialect conditioning; no token for specialized checkpoints.
  • Model switching, unloading, caching, health, retry, streaming, and history integration.
  • License metadata visible in model descriptions.

CUDA and operational hardening

  • RTX 50-series-compatible CUDA 12.8 image.
  • Both RTX 5070 and RTX 5060 Ti verified inside Docker.
  • Expandable CUDA allocation and increased shared memory.
  • Available-memory device choice for TADA.
  • Inference locking around model switching and generation.
  • Persistent profiles, outputs, model cache, and database storage.

Voicebox UX and safety

  • Arabic engine/model selection integrated into profile and generation forms.
  • History rows can be selected individually or across the entire dataset.
  • Partial select-all state is visually accurate.
  • Confirmation is required before destructive bulk actions.
  • Active generation jobs are excluded in both UI and backend.
  • Audio/version files and database rows are cleaned together.
  • The player resets if its active clip is deleted.

Normal CUDA startup

docker compose -f docker-compose.yml -f docker-compose.cuda.yml up -d --build

Voicebox is published at http://127.0.0.1:17600, avoiding conflicts with the standalone portals. Model weights remain in Docker volumes and download on first use.

Repositories, delivery, and CI

Standalone deployment

samykabu/arabicTTS contains the Dockerized F5/Habibi portals, setup guide, and the original integration research report.

Voicebox fork

samykabu/voicebox contains the native Arabic engine, CUDA deployment, TADA fixes, MSI workflow, and bulk-history capability.

The Windows workflow builds the Python server and MCP shim, produces a Tauri MSI, verifies that an installer exists, calculates its SHA-256 hash, and uploads it as a 14-day artifact. It is triggered only when a pull request affecting application, backend, Tauri, or lock files is closed with merged == true.

Known constraints and deferred work

Item Current position Why deferred
External provider API Optional later The native Docker backend now meets the immediate product need; a generic provider remains useful for remote inference.
All-checkpoint manual sweep Still recommended Automated metadata and switching tests exist, but every specialized checkpoint should still receive a final human audio-quality pass.
Full upstream regression suite Follow-up A broader Docker run had one unrelated progress-tracker failure and two legacy collection-only harness cases.
Cross-platform native bundling Best effort Docker remains the release gate until CUDA, Linux, CPU, and Apple Silicon packaging are covered consistently.
Responsible-use note: cloned voices and reference recordings are biometric data. Use only voices you are authorized to reproduce, protect persistent volumes and backups, and verify the selected checkpoint's license before commercial use.
