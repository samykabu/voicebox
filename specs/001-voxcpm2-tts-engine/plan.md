# Implementation Plan: VoxCPM2 Text-to-Speech Engine

**Branch**: `feature/001-voxcpm2-tts-engine` | **Date**: 2026-09-22 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/001-voxcpm2-tts-engine/spec.md`
**Source issue**: [samykabu/voicebox#13](https://github.com/samykabu/voicebox/issues/13) (effort 13, kept whole)

## Summary

Add VoxCPM2 as a ninth TTS engine: Apache-2.0, ~4961 MB, multilingual including Arabic,
with zero-shot voice cloning and voice design from a written description. The integration
is additive — one new backend file implementing the existing `TTSBackend` protocol, plus
registry entries — with one genuinely new piece of shared machinery: a minimal capability
channel so the app can ask the backend what an engine supports instead of keeping its own
hand-maintained lists (FR-024, settled by clarification C1Q2).

Phase 0 research materially changed the shape of this work. The two risks the source issue
led with did not hold: `voxcpm` 2.0.3 declares `requires-python >=3.10` with no ceiling,
and upstream explicitly supports CUDA, MPS and CPU with automatic fallback. So this is a
normal multi-accelerator engine, not the product's first platform-excluding one. See
[research.md](./research.md) R1 and R2.

## Technical Context

**Language/Version**: Python 3.12+ (backend, unchanged floor), TypeScript 5.x strict (app), Rust stable (Tauri shell — untouched by this feature)
**Primary Dependencies**: `voxcpm==2.0.3` pinned (T002) and installed `--no-deps` with the 8-package minimal set from the probe; existing `torch`/`torchaudio` (upstream wants `>=2.5.0`), `transformers<=4.57.6` (compatible), `huggingface-hub`, `librosa`, `soundfile`, `safetensors`
**Storage**: Local filesystem only — HuggingFace model cache, existing voice-prompt cache, SQLite for profiles. No new store, no new remote path.
**Testing**: `pytest` (`just test`, local only — not run in CI), Biome + `bun run typecheck` for the app, `ruff` for Python
**Target Platform**: Windows, Linux and macOS desktop (Tauri) plus the self-hosted backend; accelerators CUDA, ROCm, XPU, MPS and CPU
**Project Type**: Desktop application with a FastAPI backend and a React front end
**Performance Goals**: Generation must not block the UI and must go through the existing serial queue. No latency target is set for this engine; CPU inference on a 2B model is expected to be slow but usable, which the probe confirms.
**Constraints**: `numpy>=1.24,<2.0` and `transformers<=4.57.6` must survive the install; ~4961 MB download; the probe measured about 5.9 GB of peak GPU memory on short text and about 11 GB of process memory on CPU; the repository is a fork that must stay cheaply mergeable with `jamiepine/voicebox`; heavy imports must stay lazy.

**Remaining NEEDS CLARIFICATION**: none. All eight specification markers were resolved in
clarification round 2. The technical unknowns listed in [research.md](./research.md) under
"Open items" were answered by the probe (T001), and the user decided at T002
([evidence/probe.md](./evidence/probe.md), "T002 decisions"): pin `voxcpm==2.0.3`, re-score
the effort from 13 to 8, move User Story 3 to P2, and withdraw FR-023's exception, so the
engine follows the processor-fallback rule like every other engine.

## Constitution Check

*GATE: Must pass before proceeding. Re-checked after design below.*

| Principle | Status | Notes |
|-----------|--------|-------|
| I. Local-First By Default | **PASS** | Model weights, reference audio and generated audio stay on the machine. No telemetry, no new remote host. The only network access is the HuggingFace model download. Because `voxcpm` depends on `modelscope`, which the existing HuggingFace offline switch does not cover, a cached load is proven offline by a dedicated test (T046, T047) and a quickstart step, and must never fall back to the ModelScope hub. `spaces` (a HuggingFace Spaces helper) is explicitly excluded from the install set. |
| II. Consent-Bound Voice Synthesis | **NEEDS ATTENTION** | The T037 survey (2026-09-23) found no consent or disclosure affordances anywhere in the product, so none carried over. By user decision this feature adds them for every path: a responsible-use acknowledgement in the profile dialog for all three sources (FR-025); an "AI-generated by Voicebox" tag on every generated-audio surface, meaning saved files (including `/speak` and MCP speak), `/generate/stream` and the effects preview, while the user's own recordings (reference samples, the combined reference, the transcription re-encode) are never tagged (FR-026); and provenance-preserving profile export (FR-027). Voice design from a written description (FR-015) is a **new way to create a voice that bypasses the reference-audio step entirely**, and therefore bypasses the point where consent is currently implied. It must carry the same disclosure affordances as the cloning path. Tracked as a review gate below; this is not a violation, but it is the one place this feature could quietly weaken a safeguard. |
| III. Engine-Agnostic Backend Contract | **PASS** | The engine implements the existing protocol; no MCP change is needed (`engine` there is a free string validated downstream). The `TTSBackend` Protocol itself is unchanged. `options` is a backend-specific keyword on VoxCPM2's `generate`, not part of the Protocol: the generation service injects it (`backend_with_generation_options` in `backend/services/generation.py`) only for engines that declare `advanced_settings`, so existing backends are untouched. Route changes are generic: the unavailable-engine refusal is driven by the capability resolver, not the engine name. FR-024 builds the capability channel so hardware support and languages are declared once and queried, rather than adding `if engine == "voxcpm"` branches to the app. Heavy imports stay lazy inside functions, marked `# lazy: heavy import`. The accelerator declaration is honest: after R2, the engine supports the full matrix and needs no exception. |
| IV. Upstream-Trackable Fork Discipline | **PASS** | Falls under "fork-specific model support", the same category as the existing Arabic/Habibi work. The change is additive: one new backend file plus registry entries. The capability channel is the one shared-surface change; it is deliberately kept minimal and does not migrate the other seven engines, precisely to limit merge cost. |
| V. Contract-First API And MCP Surface | **NEEDS ATTENTION** | The capability channel adds a backend→app interface. It also adds two optional `GenerationRequest` fields, `voice_description` and `advanced_settings`. That obliges, in the same change: Pydantic models updated, the TypeScript client regenerated with `bun run generate:api` (never hand-edited), and `backend/README.md` updated. Additive only — no endpoint or field is removed or narrowed, so this is not a breaking change and does not need a major release. |
| Platform: Accelerator Matrix | **PASS** | R2 confirms CUDA, MPS and CPU are supported upstream; ROCm presents as CUDA to torch. On an Intel XPU or DirectML machine VoxCPM2 runs on the processor, because the vendor accepts no XPU or DirectML device; the engine stays available there with a warning that it will be slower (FR-023). CPU remains the guaranteed fallback. No declared exception is required; FR-023's exception was withdrawn by the user at T002 after the probe confirmed the processor path. |
| Platform: Model Handling | **PASS** | Download is on demand, cached, resumable, reports progress, and is never triggered implicitly — reinforced by the C1Q7 confirmation step before a 4961 MB download. |
| Workflow: Quality Gates | **PASS with a standing obligation** | `just check-js`, `bun run typecheck`, `just check-python`, `just test` and `bun run build:web` all apply. Because pytest does not run in CI, the author must run `just test` locally and say so in the PR. |
| Workflow: Documentation | **PASS** | `docs/content/docs/developer/tts-engines.mdx`, the model-management page and `CHANGELOG.md` are all in scope (FR-021, FR-022). |
| Workflow: CI Runner Policy | **PASS** | T055 edits `.github/workflows/release.yml` in its install steps only: one `pip install --no-deps 'voxcpm==2.0.3'` line in each of the three build jobs. `runs-on`, triggers and job structure are unchanged, so the repository-scoped departure recorded in red in `README.md` (GitHub-hosted runners) is unaffected. No workflow is added. |

**Gate result: PASS.** Two items are marked NEEDS ATTENTION rather than VIOLATION: both are
obligations this plan accepts and schedules (a consent review gate for voice design, and
the contract-update trio for the capability channel), not deviations requiring
justification. The Complexity Tracking table is therefore empty.

**Structure Decision**: Keep the existing backend/app split and the established
`*_backend.py` convention. No new top-level directory. The one structural addition is a
capability declaration on `ModelConfig` plus a read-only endpoint exposing it — chosen over

engine and leaves the other seven on their current lists, which keeps the upstream merge
surface small (Principle IV).

## Execution Strategy

### TDD Requirements

- [ ] **Capability resolution** (`backend/backends/base.py`, `routes/models.py`): pure logic mapping declared accelerator support plus detected hardware to available/unavailable-with-reason. Many edge cases — supported accelerator with too little memory, unsupported accelerator, no accelerator at all — and it decides whether a user can reach a crash. Test first.
- [ ] **Voice prompt cache key and pairing** (`voxcpm_backend.py`): `prompt_wav_path` and `prompt_text` must both be present or the vendor raises; the cached prompt must carry both. A cache-key collision between engines would produce the wrong voice silently. Test first.
- [ ] **Engine validation patterns** (`backend/models.py`): four identical regexes that must accept `voxcpm` and keep rejecting unknown values. Cheap to test, easy to get subtly wrong in one of the four.

### Parallel Execution Opportunities

- [ ] The **dependency probe** must complete alone, first. Its findings change the work in every other stream, so nothing runs in parallel with it.
- [ ] After the probe: **backend engine** (`voxcpm_backend.py` + registry) and **install/packaging** (`requirements.txt`, justfile, `build_binary.py`) touch disjoint files and can proceed in parallel.
- [ ] The **capability channel** (backend half) must land before the **frontend availability UI** consumes it — sequential, and the seam between them is the generated client.
- [ ] **Docs** (`tts-engines.mdx`, model-management page, `CHANGELOG.md`) are independent of all code streams once behaviour is settled.
- [ ] **Frontend surface** work splits cleanly: the voice-description input (`FloatingGenerateBox.tsx`) and the download-confirmation dialog (`ModelManagement.tsx`) share no files.

### Human Checkpoints

Under `execution.checkpoints: required-only`, routine phase transitions are automatic.
These are the explicit gates that still pause:

1. **After the dependency probe** — its findings decide `size_mb`, the memory threshold, the real sample rate, whether CPU and MPS are usable, and whether the numpy pin survives. Several could change scope. Human review of the findings before implementation proceeds.
2. **Before the capability channel's API shape is fixed** — it is a public contract surface under Principle V and is consumed by the generated client.
3. **Voice design consent review** (Principle II) — before voice-from-description ships, confirm it carries the same disclosure affordances as the cloning path.
4. **Before merge** — final review against spec, with `just test` run locally and stated in the PR.

### Review Gates

- [ ] **Capability channel contract** (`contracts/engine-capabilities.md`, Pydantic models, generated client): review before the frontend consumes it. Principle V.
- [ ] **Voice design path** (`FloatingGenerateBox.tsx`, the `voice_description` request field and its backend handling): review for consent and disclosure parity. Principle II.
- [ ] **`--no-deps` dependency set** (`requirements.txt`, justfile both paths): review before merge — a wrong entry here silently breaks four other engines for every developer.
- [ ] **Frozen build changes** (`build_binary.py`, `torchcodec`/FFmpeg): review before merge; failures surface only in a packaged build.

## Post-Design Constitution Re-Check

Re-evaluated after the Phase 1 artifacts below were written, and refreshed after
implementation (2026-09-23). **Still PASS.** The design adds one read-only endpoint and
capability fields on an existing dataclass; it removes nothing, narrows nothing and
introduces no new remote path, table or column. One exchange format changed: the profile
export manifest moves from 1.0 to 1.1 (FR-027). The change is additive — five provenance
fields next to the existing ones — and a 1.0 manifest still imports, as a cloned profile.
Generated WAVs gain an INFO metadata chunk (FR-026); the audio samples are unchanged.
Principle III is better satisfied after the design than before it, because the capability
channel replaces hand-maintained app-side lists for this engine rather than adding to them.
